RAG가 왜 틀린 답을 내는지
찾아내고, 스스로 고칩니다

AgentDoctor는 검색·생성 파이프라인을 검사해 어디서 문제가 생기는지 짚어내고, 검색 파라미터를 근거에 따라 자동으로 조정합니다.

RAG 점수만 매기는 도구가 아닙니다 직접 고쳐서, 나아졌다는 걸 전후로 증명합니다.
01
진단 Diagnose

검색이 정답을 놓쳤는지, 생성이 지어냈는지, 컨텍스트 구조가 문제인지 — 원인을 종류별로 분류합니다.

02
처방 Prescribe

발견한 원인에 맞춰 top_k·청크 크기 같은 설정을 근거 기반으로 조정할 후보를 정합니다.

03
개선 Improve

전후 지표를 비교해 실제로 나아졌는지 확인하고, 오히려 나빠지면 되돌립니다.

실행 로그 안에 정답(ground_truth)이 들어 있어 골든셋 파일 없이도 전체 진단이 가능합니다.

이미 운영 중인 RAG의 실행 로그를 올리면, 파이프라인을 바꾸지 않고 그대로 진단합니다. top_k·청크 크기 같은 설정은 로그의 config 필드에 담아 주세요 — 권고에 현재값이 함께 실립니다.

올리기 전에 — 로그에 민감정보가 들어 있지 않은지 확인해 주세요
  • 실행 로그에는 실제 사용자 질문·검색된 문서 원문·답변·정답지가 그대로 담깁니다.
  • 채점을 위해 질문·컨텍스트·답변이 LLM 심판 API로 전송됩니다.
  • 진단서의 “실패한 검증 질문” 섹션에 로그 원문이 그대로 실립니다 — 진단서를 공유하면 로그 내용도 함께 나갑니다.
  • 업로드한 파일은 서버의 uploads/<run_id>/에 남고 자동 삭제되지 않습니다.
  • 진단에는 50~150건이면 충분합니다 — 전체 로그 대신 익명화한 표본을 권합니다.
파일 형식 안내

운영 중인 RAG가 실제로 주고받은 기록입니다. JSONL — 한 줄이 요청 1건. question·answer 두 개만 있어도 진단은 시작되고, 나머지를 채울수록 원인을 좁힙니다.

{"question": "환불 규정이 뭐야",
 "answer": "환불은 구매 후 7일 이내에...",
 "contexts": ["검색된 문단 1", "검색된 문단 2"],
 "config": {"top_k": 5, "chunk_size": 512}}

반드시 있어야 하는 것

  • question필수
    사용자가 실제로 던진 질문 원문. 골든셋과 짝을 맞추는 키로도 쓰입니다.
  • answer필수
    그 질문에 RAG가 내놓은 최종 답변.
    두 필드만 있는 경우 동문서답(질문과 딴소리) 검사까지만 가능합니다 — 환각인지 검색 실패인지는 갈라내지 못합니다.

넣으면 진단이 깊어지는 것

  • contexts권장검색이 가져온 문단 원문
    문자열 배열이거나 {"text": "...", "score": 0.82} 형태. 전체 로그의 절반 이상에 있어야 적용됩니다.
    켜지는 진단 · 환각 실측(답이 근거 밖으로 나갔는지)과 책임 분리 — 틀린 답이 검색이 못 찾아온 탓인지 찾아왔는데 생성이 망친 탓인지 갈라냅니다. 리포트의 원인 라벨 대부분이 여기서 나옵니다.
  • score선택contexts 항목 안의 유사도 점수
    각 문단이 몇 점으로 뽑혔는지. {"text": "...", "score": 0.82} 형태로 넣습니다.
    켜지는 진단 · 랭킹 문제(근거는 왔는데 뒤로 밀림)와 커버리지 문제(애초에 안 옴)를 구분합니다 — 앞쪽이면 리랭커, 뒤쪽이면 top_k·청킹으로 처방이 갈립니다.
  • config권장top_k · chunk_size 등 현재 설정
    시스템 설정이라 한 줄에만 넣어도 됩니다(모든 줄이 같은 값일 때 대표값으로 씁니다).
    켜지는 진단 · 권고 카드가 구체적인 수치 제안이 됩니다 — “청크가 큽니다”가 아니라 “chunk_size 512 → 768”. 없으면 증상까지만 알려주고 목표값은 비어 있습니다.
  • feedback선택사용자 만족/불만 표시
    “도움 안 됨” 같은 실제 반응이 남아 있다면.
    켜지는 진단 · 불만족 케이스를 우선 표본으로 삼아, 사용자가 실제로 아파한 질문부터 원인을 파고듭니다.
  • ground_truth gold_contexts선택골든셋을 로그 안에 직접
    정답과 정답 근거를 별도 파일 대신 로그 줄에 바로 넣는 방식입니다.
    켜지는 진단 · 골든셋 탭과 똑같은 진단이 켜지고, 골든셋 파일 업로드를 생략할 수 있습니다. 보통은 정답지를 따로 관리하니 골든셋 파일 쪽이 편합니다.
  • latency_ms timestamp선택
    응답 시간과 시각. 진단 판정에는 쓰이지 않고 리포트의 참고 정보로만 실립니다.

사람이 만든 정답지이고, 진단의 기본 입력입니다. 이게 있어야 “틀렸다”를 추측이 아니라 대조로 확정합니다. XLSX · CSV · JSONL · JSON 모두 받으니, 이미 쓰는 테스트셋이 있으면 그대로 주셔도 됩니다.

question,ground_truth,gold_contexts
환불 규정이 뭐야,구매 후 7일 이내 전액 환불,"제7조(환불) 구매일로부터 7일 이내…"

반드시 있어야 하는 열

  • question필수
    실행 로그의 질문과 자동으로 짝지어집니다 — 공백·끝 문장부호·대소문자 차이는 무시하므로 토씨까지 맞출 필요는 없습니다. 매칭된 건수만 골든셋 기반 진단에 들어가고, 못 맞춘 항목은 버려지지 않고 리포트에 집계됩니다.
  • ground_truth필수정답 텍스트
    그 질문의 옳은 답. 문장이면 충분합니다.
    켜지는 진단 · 정답 일치도와 검색 정밀도·재현율이 측정되면서 환각 판정이 ‘예비’에서 ‘확정’으로 올라갑니다. 또 “근거엔 충실한데 답이 틀린” 경우 — 설정이 아니라 문서 자체가 낡거나 빠진 상황 — 를 따로 잡아냅니다.
    정답이 없으면 검색축 원인 3종이 침묵하고 환각은 ‘예비’에 고정됩니다 — 원인 7종 중 3종까지만 나오고, 임베딩·청킹 처방도 없습니다. 무엇보다 종합점수 자체가 나오지 않습니다(답이 맞았는지 대조할 수 없어 신뢰도 축을 못 잽니다). 그래서 이 화면에서는 정답을 면제하지 않습니다.

넣으면 진단이 깊어지는 열

  • gold_contexts권장정답 근거 문단
    정답의 출처가 된 문단의 원문 텍스트를 넣습니다 — 청크 ID가 아닙니다(텍스트 겹침으로 판정하기 때문). 여러 개면 배열로.
    켜지는 진단 · 검색축 진단 3종이 열립니다 — 엉뚱한 문단을 물어왔는지, 근거가 없어서 답을 포기한 건지, 근거는 손에 쥐고도 답을 못 만든 건지. 임베딩·청킹 처방은 이 판정에서만 나옵니다.

열 이름은 관용적으로 받습니다

  • 질문 — question · q · query
  • 정답 — ground_truth · gold_answer · answer
  • 근거 — gold_contexts · evidence · context

두 파일 공통 · 권장 크기

  • 50~150건이 적당합니다 — 원인 라벨별로 판단이 설 만큼 쌓이면서, 사람이 채우기엔 부담 없는 크기입니다
  • 300건을 넘으면 매칭되는 레코드마다 검색축 지표를 추가로 재느라 비용이 커져 진단을 진행하지 않습니다
